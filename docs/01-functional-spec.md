## 2. 핵심 인물 모델 — Person / UserAccount 분리

> 자녀의 "데이터 대상 → 로그인 사용자" 전환 시 **데이터 마이그레이션이 발생하지 않도록** 사람 자체와 로그인 수단을 분리한다.

| 개념 | 설명 | 예시 |
|------|------|------|
| **Person** | 가족 구성원 그 자체. 모든 데이터(author/subject 등)가 가리키는 대상 | 아빠, 엄마, 첫째 |
| **UserAccount** | 로그인 수단(선택적). 로그인하는 사람만 가짐 | 아빠 계정, 엄마 계정 (첫째는 없음 → null) |
| **FamilyMembership** | Person이 어느 Family에 어떤 역할로 속하는지 | |

- 모든 author/subject 참조는 **Person**을 가리킨다 (UserAccount 아님)
- 자녀: Person으로 먼저 존재, UserAccount 없음 → 성장 후 UserAccount 1개 연결만으로 전환 완료 (**데이터 이관 0**)

## 3. 권한 모델 — author / subject / visibility 3분리

| 축 | 의미 | 참조 | 형태 |
|----|------|------|------|
| **author** | 누가 만들었나 | Person | 단일 |
| **subject** | 누구에 관한 것인가 | Person | **일정·일상기록=다중 / 가계부=단일** |
| **visibility** | 누가 볼 수 있나 | (아래 레벨) | enum 프리셋 |

### subject 다중값 처리
- **일정·일상기록**: 다대다 연결 (예: 가족여행 = 아빠+엄마+첫째 모두 subject)
- **가계부**: 단일 (이 지출은 누구를 위한 것 하나) — 과설계 방지

### Visibility 레벨

**일정 · 일상기록 (4단계)**

| 레벨 | 누가 보나 | 예시 |
|------|-----------|------|
| 순수 개인(private) | 작성자 본인만 | 회의, 개발일정 |
| 공유 개인(shared-personal) | 본인 + 지정 구성원(기본: 배우자) | 출장, 야근 |
| 부모 공유(parents-only) | 부모들만 (자녀 제외) | 자녀 선물, 민감 정보 |
| 가족 공동(family) | 전 구성원 | 가족 여행, 외식, 기념일 |

**가계부 (2단계 + 확장 여지)**

| 레벨 | 누가 보나 | 비고 |
|------|-----------|------|
| 개인(private) | 본인만 | 개인 용돈, 사적 지출 |
| 부모 공유(parents-only) | 부모들만 | 생활비, 공과금 |
| 가족 공동(family) | 전 구성원 | 자녀 용돈 등 — **구조만 열어둠, 미동작** |

### Visibility = ACL 프리셋 (중요 설계 원칙)
- visibility enum은 **"누가 볼 수 있나(사람 집합)"의 프리셋**으로 취급
- 코드에서 visibility → 사람 집합으로 변환하는 계층을 거침 (내부적으로 ACL처럼 동작)
- **MVP**: enum 프리셋만 (위 4단계)
- **확장**: "배우자+첫째만" 같은 커스텀 조합이 필요해지면 AccessControl 테이블 추가
  → 구조만 열어두고 MVP에선 미구현

### 뷰어별 표시 설정
- 공유개인 일정을 **상세까지 볼지 / 요약만 볼지는 "보는 쪽(뷰어)"이 본인 설정에서 결정**
- 사용자별 표시 환경설정 (특정 구성원 일정의 표시 수준)

### 적용 예시 (검증)

| 항목 | author | subject | visibility |
|------|--------|---------|------------|
| 내 개발 회의 | 나 | 나 | 순수개인 |
| 내 부산 출장 | 나 | 나 | 공유개인 |
| 가족여행 | 나 | 나+배우자+첫째 | 가족공동 |
| 자녀 예방접종 | 나 | 첫째 | 부모공유 |
| 자녀 생일선물 구매(가계부) | 나 | 첫째 | 부모공유 |

## 4. Family 모델 (멀티테넌트 기반)

- **모든 데이터 테이블에 `family_id` 필수**
- `Person ↔ FamilyMembership ↔ Family` — Person이 여러 Family 소속 가능
  (예: '우리 가족'과 '부모님 가족' 동시)
- 파일 저장 경로도 family_id 기준 분리
- **권한 검증 2단계**: ① 그 Family 멤버인가 → ② Family 내 author/subject/visibility

### 구성원 Role

| Role | 설명 |
|------|------|
| 부모(parent) | 모든 공동 데이터 관리, 자녀(Person/계정) 관리 |
| 자녀(child) | 초기엔 데이터 대상(Person, UserAccount 없음) → 성장 후 계정 연결 |

## 5. 기능별 명세

### ① 가계부
- **scope**: 개인 / 부모공유 2단계 (가족공동은 구조만)
- **신규 입력 기본값**: 개인 (UI에서 변경)
- **입력 경로 3종**: ① 수동 ② 텍스트 붙여넣기 ③ 텔레그램(Hermes)+영수증 이미지
- **자동 추출**: 멀티모달 LLM 권장, **확인 게이트 후 저장**
- 카테고리 분류, 통계(개인/부모공유/전체, 월별·카테고리별)

**계좌 / 자산 모델**
- **계좌/결제수단(Account)**: 현금, 신한카드, 현대카드, 네이버페이, 카카오페이 등
- **자산 유형**: 은행 / 증권 / 현금
- **거래 유형**: 수입 / 지출 / **이체(transfer)** — 이체는 통계에서 제외
- 총자산·월 지출·저축률 산출 가능

### ② 일상기록
- **scope**: 4단계, **subject 다중**
- **혼합형 뷰**: 피드(인라인) / 캘린더 — 앨범(사진 전용 그리드)은 미구현, 추후 과제(07 §6)
- 글 + 사진 포스트
- 외장 SSD 저장 (StorageService, 상대 키 방식)
- **태그 시스템**: #여행 #육아 #건강 등 (가계부와 공통 태그)

### ③ 일정관리
- **scope**: 4단계, **subject 다중**
- **개인 구글 캘린더 양방향 동기화** (순수 개인 포함 전체)
- **구글 동기화 필드 (Schedule에 선반영)**: `google_event_id`, `sync_status`(SYNCED/PENDING/CONFLICT/DELETED_REMOTE), `last_synced_at`
- 할 일 / 리마인더, 반복 일정
- **참석자(Participant)**: 일정에 복수 구성원 연결. subject와 별개로 "실제 참석자". **RSVP 보류**
- **알림(푸시) 없음** — 조회는 앱 또는 텔레그램(Hermes) 질의

### ④ 이벤트 묶음 (Collection)
- 여행/이벤트 단위로 지출·기록·일정 선택적 묶음
- 묶음 리뷰 (예: "여름휴가: 총지출 OO, 사진 OO장, 기록 OO개")
- 평소엔 날짜 기준으로만 모임, 묶을 때만 연결
- 묶음 생성은 **일정 화면이 기준**(작성 시 이름+태그로 생성), 가계부·기록은 기존 묶음에 연결만
- **태그**는 Schedule이 아닌 **Collection 자체에** 부여(가계부/일상기록 태그와 같은 `Tag` 도메인 재사용) — 비슷한 이벤트를 태그로 검색해 묶음을 재사용하기 위함. 같은 태그의 묶음을 서로 다른 날짜에서도 재사용 가능(묶음이 날짜에 고정되지 않음)

### ⑤ 통합 타임라인 뷰
- 특정 날짜 = 그날의 **지출 + 일정 + 일상기록 + 사진**이 한 화면에
- 시스템 핵심 경험

### ⑥ 입력 UX
- 앱 내 **빠른 입력 화면**
- **위젯** → 탭 시 빠른 입력 화면으로 이동 (iOS/Android 공통, 위젯 내 직접 입력 아님 — iOS 제약)
- 텔레그램(Hermes) 병행

## 6. 사진 / 파일 모델

- 저장: 외장 SSD, **상대 키** (`family_3/2026/05/photo_abc.jpg`)
- **메타데이터 (Photo 테이블)**: `photo_hash`(중복제거·무결성), `width`, `height`, `taken_at`(촬영시각·타임라인 정렬 기준), `file_size`, `mime_type`
- ※ `taken_at`은 업로드 시각이 아닌 EXIF 촬영 시각

## 7. 데이터 안전성 (양보 불가)

### Soft Delete (최우선)
- 모든 주요 엔티티에 `deleted_at`, `deleted_by` / **물리 삭제 금지**
- 처음부터 모든 조회 쿼리에 적용

### 변경 이력 (간소화 Audit)
- 목적: **실수 추적·복구** (분쟁 증거용 아님)
- 누가/언제/무엇을 변경했는지 → 잘못 수정 시 되돌리기
- 풀 감사 로그는 과설계로 보류

### 백업 전략
- **사진**: 원본 SSD + 주기 백업 SSD(rsync) 2중화, 가능하면 R2 오프사이트 1벌
- **DB (사진보다 우선 복구)**: MySQL Dump **매일 새벽 / 7일 보관 / 월 1회 장기보관**
  → DB가 없으면 사진 파일이 멀쩡해도 의미 부여 불가

## 9. 개발 범위 / 로드맵

### MVP (구글·텔레그램 포함 — 현재 사용 편의 유지)
- Family / Person / UserAccount / FamilyMembership
- 가계부 (계좌·자산·이체 포함)
- 일정관리 (**구글 캘린더 양방향 동기화 포함**)
- 사진 포함 일상기록
- 통합 타임라인 뷰
- **텔레그램(Hermes) 입력 + 영수증 추출 포함**

> **구현 순서 (리스크 낮은 순, 범위 축소 아님)**
> 1. 코어 (Family/Person, 가계부·일정·일상기록 직접입력, 통합 타임라인)
> 2. 텔레그램 입력 (Hermes 확장, 비교적 빠름)
> 3. 구글 캘린더 양방향 동기화 (가장 까다로움, 마지막에 충분한 시간 확보)
> → 중간에 막혀도 그 앞까지는 사용 가능한 상태 유지 (fail-safe)

### V1.5
- **통합 검색** — 일정/가계부/일상기록/사진 횡단 ("제주" → 전부 검색)
  ※ 우선순위 상향. 스키마에서 태그·날짜·텍스트 인덱스 미리 대비

## 11. DB 설계 원칙 (다음 단계 진입점)
